The whole thing in one breath

A note becomes a 384-pixel-wide, 1-bit image. The image becomes 48-byte rows. Commands become MXW01 frames, and the rows stream to GATT characteristic ae03. A local daemon owns the BLE connection; the command line, the web page, and the agent are just front doors.

01 / bits

A dot is a decision.

Start at the paper. The print head is a row of 384 tiny heating elements. For each row of the image, each element is either on or off. On means heat; heat turns the thermal coating black. That is the entire display: 384 on/off decisions, repeated down the paper.

One decision is a bit. Eight decisions are a byte. 384 decisions are 48 bytes. The printer never receives the letter “A”; it receives a pattern of bits that your renderer decided should be black.

This is why the first question is not “how do I send a string?” but “what pixels do I want, and how are they packed?” Hex is just shorthand for four bits: 0x5D is 93, and one byte is exactly two hex digits. Endianness is the order of bytes in a multi-byte number. The MXW01 uses little-endian 16-bit lengths, so 208 is D0 00, not 00 D0.

The same eight bits can mean the number 65, the letter A, or eight heater decisions. Meaning comes from context.

Two conventions will bite you. The printer packs pixels least-significant-bit first, and it treats 1 as black. Pillow’s 1-bit mode does the opposite on both counts: 0 is black and pixels are packed most-significant-bit first. The driver has to flip both.
02 / machine

The printer is a small computer.

Before the radio, there is a microcontroller running firmware, a buffer for image rows, sensors for paper and temperature, a battery, and a print head. It sleeps. It accepts one Bluetooth Low Energy (BLE) connection at a time. It can run out of paper.

That means the printer is stateful. You are not writing to a file; you are holding a conversation with a small machine that has physical needs. The useful analogy is a tiny restaurant: you can order from the menu, but you cannot rearrange the kitchen.

Data transfer is layered. Each layer adds an envelope: voltage timing, radio packets, GATT operations, protocol frames, raster rows. The layer above does not need to know the layer below’s details. That is why a web form can eventually heat a dot without knowing anything about radio modulation.

03 / ble

The invisible cable.

Bluetooth Low Energy replaces the wire with a low-power 2.4 GHz radio. A peripheral advertises a small packet: “I am here, my name is MXW01.” A central — your laptop — scans, connects, and discovers the GATT database.

Think of advertising as a shop sign, the connection as walking in, and GATT as the menu. The sign is not the menu. In BLE terms, the printer is the peripheral (the advertiser) and the laptop is the central (the scanner and connector). The MXW01 advertised af30, but the real command service was ae30. This is the most important debugging lesson in the project: advertising is a hint; the connected GATT table is the contract.

GATT is not a byte stream. It is a set of labelled characteristics. Underneath, the Attribute Protocol (ATT) defines the read, write, and notify operations. GATT organizes data into services (groups of related values) and characteristics (the individual values). A characteristic has a UUID, a set of properties (read, write, notify), and a value. Descriptors add metadata; the Client Characteristic Configuration Descriptor (CCCD) is the descriptor that turns notifications on or off.

You write a value to ae01, subscribe to notifications on ae02, and stream image rows to ae03. Writes are write-without-response, so the ATT layer does not guarantee delivery; the printer’s own protocol replies are the feedback.

Each service and characteristic has a UUID, a 128-bit identifier. The short ae30 form is shorthand for 0000ae30-0000-1000-8000-00805f9b34fb: the 16-bit alias sits inside the standard Bluetooth base UUID. The code looks up characteristics by UUID, not by a hard-coded handle (the slot number where an attribute lives), because handles can differ between devices and firmware versions.

Lab 03 — the filing cabinet advertisement → real GATT
The maximum transmission unit (MTU) is a maximum, not a target. The printer negotiated 185 bytes, but the image protocol writes 48-byte rows with a 10 ms pause. The print head and firmware set the pace; “send faster” is not automatically better. The connection interval — how often the two sides exchange packets — is the other half of the timing story: a longer interval saves power but adds latency.
04 / protocol

The printer’s language.

Commands are frames. A frame is an envelope with a manifest and a tamper seal: a magic header, a command byte, a length, a payload, a cyclic redundancy check (CRC), and a terminator.

The MXW01 frame is 22 21 <cmd> 00 <len LE16> <payload> <crc8> FF. LE16 means a two-byte little-endian integer: low byte first, then high byte; 208 is D0 00, not 00 D0. The length counts only the payload. The CRC covers only the payload. The command byte says what the payload means. The printer replies with the same header; a notification may contain part of a frame, multiple frames, or a frame plus extra bytes, so the driver buffers and reassembles.

Lab 04 — build a frame, watch the CRC live hex
command length payload CRC-8 terminator

CRC-8 is a checksum, not encryption. It detects accidental corruption. The variant matters: polynomial 0x07, initial value 0x00, no reflection, final XOR 0x00, payload only. A different “CRC-8” can produce a different byte and the printer will silently ignore the frame.

The print sequence is: status (A1) → intensity (A2) → print request (A9) → image rows on ae03 → flush (AD) → wait for complete (AA). A9 means “job accepted”; AA means “physical print finished.” Missing AA is not proof of failure.

Feed is part of the raster, not an afterthought: the driver appends blank rows and includes them in the A9 height, so the tear-off margin is deterministic. For a 128-row render with 80 feed rows, the printer is told to print 208 rows.

05 / render

From text to dots.

The printer is a 384-pixel-wide, 1-bit display. Rendering is the part users actually see: text is drawn on a grayscale canvas with real fonts and measured widths, then thresholded to black and white.

Photos are dithered to suggest gray. Quick-response (QR) codes are resized with nearest-neighbor interpolation so the module edges stay crisp. The renderer is where a receipt becomes readable rather than a smudge.

Same eight pixels, two conventions. The driver flips the polarity and reverses the bit order before sending. That is why a picture can look perfect in preview and come out inverted or shifted on paper.

Two typography bugs made the rendering layer concrete. First, baseline alignment: words without ascenders (aaa) sat higher than words with ascenders (haa) because each run was anchored to its own glyph box top. The fix was to compute a shared baseline from font metrics and draw every run with anchor="ls".

Top alignment: the short word floats above the shared line.

Second, receipt columns: padding with spaces assumes every character has the same width. Proportional fonts and mixed runs break that assumption. The fix was to split on two or more spaces, measure the right column in pixels, and draw it at the right edge.

In a 1-bit medium, layout is not decoration. It is the difference between a receipt and a smudge. The radio is commodity engineering; the renderer is the product.
06 / bridge

One printer, three front doors.

A single BLE connection cannot be shared by a command-line tool, a browser, and an agent that each connect directly. The bridge is a local daemon that owns the connection and exposes a small local HTTP (Hypertext Transfer Protocol) application programming interface (API).

The command-line interface (CLI), web user interface (UI), and OpenCode plugin all go through the same printer manager. That consistency is the point: a fix in the renderer improves every front door. The same manager also supports the LuckPrinter/DP-L1S family, a serial Epson Standard Code for Point of Sale (ESC/POS) path, and a mock printer for development; protocol auto-detection picks the right transport.

07 / bugs

What broke, and what it taught.

Every bug was a layer boundary in disguise. The symptom looked like “the printer is broken”; the cause was almost always one wrong assumption about a lower layer.

wrong family

The device name is a hint.

The MXW01 is not a LuckPrinter. GATT layout is the fingerprint, so the manager detects the mismatch and retries with the suggested protocol.

red herring

af30 is not ae30.

The advertised service was not the command service. Connect, enumerate GATT, and use the real table: ae30/ae01/ae02/ae03.

checksum

“CRC-8” is ambiguous.

The Dallas/Maxim variant gives 0xA1 for 123456789; this protocol’s non-reflected 0x07 variant gives 0xF4. Specify every parameter.

raster

Bit order and polarity both flipped.

Pillow packs 0 = black, MSB first. The MXW01 wants 1 = black, LSB first. The driver inverts each byte and reverses the bit order.

typography

Top alignment is not baseline alignment.

Each text run was anchored to its own glyph box top. A shared baseline from font metrics fixed the jitter and got a regression test.

layout

Spaces are not a ruler.

Receipt amounts padded with spaces did not line up. The fix measures the right column in pixels and draws it at the right edge.

acks

Missing AA is not failure.

Notifications can be dropped. The print may still have happened. Report acked: false, but do not claim the paper is blank.

state

The printer sleeps and owns one connection.

BLE peripherals are stateful and single-owner. Wake the printer, force-quit the phone app, and retry. This is physical state, not a web bug.

  1. Check physical state: power, paper, cover, battery, sleep, phone app.
  2. Scan. Confirm the device is advertising; note name, address, signal strength (RSSI), services.
  3. Connect and dump GATT. Record every service, characteristic, property, and handle.
  4. Identify write, notify, and data characteristics. Do not trust the advertisement.
  5. Subscribe to notifications. Confirm the CCCD write succeeds.
  6. Send a known query, such as A1 00, and capture the raw reply.
  7. Find the framing: magic, length, command, checksum, terminator.
  8. Change one variable at a time. Use known-answer tests. Preview before printing.
08 / lessons

Why it matters.

The interesting part is not that a cheap printer can be driven from Python. It is what the exercise says about the devices around us, and about the software we build on top of them.

The app is the driver. These printers are not self-describing. The vendor app contains the protocol knowledge, the rendering rules, and the quirks. When the app dies or demands an account, the hardware becomes e-waste unless someone reverse-engineers the GATT layer.

Advertisement is not the API. The real contract is the GATT table after connection, plus the byte protocol on top. Generic BLE tools should always enumerate, not trust the scan packet.

Throughput is not MTU. The radio can carry 185-byte packets, but the printer expects 48-byte rows with a delay. The print head sets the pace. Measure the whole pipeline, not the radio’s theoretical maximum.

A local daemon is a device broker. Single-connection peripherals need an owner. The broker serializes access, caches state, retries, and gives every front door a stable API. The pattern generalizes to scanners, cameras, serial gadgets, and lab equipment.

Constraints clarify. No color, no grayscale, 384 pixels wide. A receipt forces prioritization. Agent-written output is better when it is short, structured, and physical.

Local-first is repairable. No cloud, no account, no vendor app. The API binds to 127.0.0.1; previews stay on the machine. For a device that prints private notes, that matters.

The one-sentence version. A cheap printer is a small computer with a radio and a secret language; once you learn the language, you can put it behind a local API, a web UI, and an agent tool — and a device that only worked with a phone becomes part of your workflow.

Situation

A small thermal printer works only through a phone app. The goal is to print from a laptop, a web page, and a coding agent.

Complication

The obvious assumptions are wrong: the advertised service is not the API, commands are binary, and text layout is pixel layout.

Resolution

Model five layers — physical, radio, GATT, protocol, software — and build a renderer, a protocol encoder, a GATT client, and a broker.

01

Physics first: the output is heat.

Before there is a packet, there is a resistor, a pulse of current, and a paper coating that changes color when it gets hot enough. The protocol exists to control that physics.

Thermal paper is a base sheet coated with a colorless dye and a developer. Above a threshold temperature they react and the coating turns dark. Darkness depends on heat, time, pressure, and paper — which is why density changes energy, not color.

The print head is a line of 384 tiny resistors. Current through each resistor becomes heat. A shift register and latch select the row; a strobe pulse times the heat; the paper advances one row. At 203 dpi, 384 dots span about 48 mm.

For a reader who has never studied electronics: voltage is electrical pressure, current is flow, and resistance is restriction. Power is energy per second; energy is total heat. Ohm’s law is V = I × R; power is P = V × I. A logic 1 is a voltage range that turns a switch on; 0 turns it off. A microcontroller is a small computer; firmware is its program; a driver is software that speaks to hardware.

Each dot is a binary decision: heat or no heat. 384 decisions are 384 bits, or 48 bytes. Gray is approximated by dithering or multi-level modes; the MXW01 monochrome path uses one bit. The printer is also a state machine: paper sensor, cover, battery, thermistor, sleep, and one BLE connection.

The data format is a direct consequence of the hardware: 384 heaters, one bit each, 48 bytes per row, one row at a time. There is no “page description language” hiding in the print head.

So what? The printer’s physical constraints define the contract your software must satisfy: 384 pixels wide, 1 bit per pixel, 48 bytes per row, and a paper-feed model measured in rows. Every later layer exists to deliver those bits at the right time.
02

The radio link: BLE is a packet service.

Bluetooth Low Energy does not replace a wire with a continuous stream. It replaces it with a scheduled exchange of small packets on a shared radio channel.

BLE uses the 2.4 GHz band, shared with Wi-Fi and classic Bluetooth. It uses 40 channels — three advertising, 37 data — and hops to reduce interference. It modulates with GFSK (Gaussian Frequency-Shift Keying). The central (laptop) scans and initiates; the peripheral (printer) advertises and waits. These are radio roles, not power rankings.

Before any connection, the printer advertises a small packet on the advertising channels. The legacy payload is at most 31 bytes, packed as AD structures: length, type, value. A typical packet carries flags, the device name, and a list of service UUIDs. A service UUID is a label; it is not a command and it does not open a pipe.

Exhibit 2What an advertisement physically contains
02 01 06  06 09 4D 58 57 30 31  03 03 30 AF
BytesMeaning
02 01 06Flags: length 2, type 1; value 0x06 (LE general discoverable, BR/EDR not supported).
06 09 4D 58 57 30 31Complete local name: length 6, type 9; ASCII “MXW01”.
03 03 30 AFComplete list of 16-bit service UUIDs: length 3, type 3; UUID 0xAF30, little-endian.

Illustrative advertisement. Real firmware may add transmit power, manufacturer data, a scan response, or other AD structures. The key point is that af30 is a service label inside this broadcast payload — not a command channel.

To connect, the central sends a CONNECT_IND with an access address, CRC initialization value, connection interval, peripheral latency, supervision timeout, channel map, and hop increment. The two sides then wake at each connection event, exchange packets on a data channel, and hop. The connection interval is how often those events occur; latency lets the peripheral skip events; supervision timeout is when the link is declared lost.

Every transmission is a link-layer packet: a preamble, a 4-byte access address, a PDU, and a 3-byte CRC. The controller builds and checks these; the application never does. Inside a data packet, L2CAP adds a length and channel ID, then ATT carries read, write, notify, or discovery PDUs. HCI is the boundary between the OS host and the radio controller. Bleak talks to the OS; the OS and controller handle HCI, scheduling, packets, and retries.

MTU is the largest ATT payload. The default is 23 bytes; three bytes of ATT header leave 20 bytes of value. This printer negotiated 185 bytes, so 182 bytes of value — but the image protocol still writes 48-byte rows. The MTU is a ceiling, not a target.

Reliability is layered. The link layer uses CRC and acknowledgements, and retransmits within the connection. At ATT, a notification is unacknowledged; it can be missed if the client did not subscribe or the link dropped.

So what? BLE gives you a reliable packet pipe, not a reliable application conversation. Your code must still manage subscriptions, timeouts, retries, and physical state. The radio is not the hard part; the state machine on top of it is.
03

The device layer: GATT is the printer’s API.

Once the radio link exists, the laptop needs a way to name and reach the printer’s capabilities. GATT is that naming system and database.

GATT stands for Generic Attribute Profile. It is built on ATT, the Attribute Protocol. The printer’s firmware holds an attribute table: rows with a 16-bit handle (address), a UUID (type), permissions, a value, and a callback.

The table is organized into services (groups) and characteristics (values with properties). A descriptor is metadata; the CCCD is the descriptor that switches notifications. UUIDs are names; handles are addresses. The printer assigns handles, so a driver discovers the table and maps UUIDs to handles.

The client sends ATT discovery requests — “read by group type” for services, “read by type” for characteristics — and the printer returns handle ranges and UUIDs.

Handles are illustrative. The UUIDs and properties are the contract; the handle numbers are assigned by the printer and should be discovered at runtime.

A GATT write can be a Write Request (the server returns an ATT response) or a Write Command (no ATT response). The MXW01 uses write-without-response for commands and image data, so feedback comes from its own protocol replies, not from ATT.

A notification is an unacknowledged value push; an indication is acknowledged at the ATT layer. To receive notifications, the client writes 0x0001 to the CCCD; indications use 0x0002. Without that subscription, the printer has no reason to send.

Physically, a write is a packet with a handle and a value. The GATT server checks permissions and invokes the callback: ae01 parses a frame, ae03 appends image bytes, ae02 pushes a notification.

So what? GATT turns a radio link into a stable, named API. UUIDs tell you what a capability is; handles tell you where it lives; properties tell you what operations are allowed. Discovery is the step that binds the names to the addresses.
04

The red herring: advertised service vs command service.

This is the single most important distinction in the build. The advertisement and the command service are different objects, in different layers, carrying different bytes.

The MXW01 advertisement listed a service UUID, af30. Commands lived under ae30. It is tempting to read that as “the printer changed its address” or “the app uses a hidden channel.” Neither is what happens.

Physically, af30 is a few bytes inside a broadcast packet. It is an AD structure of type “complete list of 16-bit service UUIDs.” The radio sends it on an advertising channel; anyone nearby can hear it. There is no connection, handle, GATT operation, or command queue. It is a label the firmware chose to broadcast — a claim about a service, not a route to it.

Physically, ae30 is a row in the printer’s GATT attribute table after the connection is established. It groups characteristics such as ae01 (commands), ae02 (notifications), and ae03 (image data). Each has a handle assigned by the printer. A command is an ATT Write Command addressed to ae01’s handle, with a specific value.

Why differ? Advertising space is tiny; firmware may advertise a related profile or a default/stale service list. Only GATT discovery is authoritative. The advertisement is a shop sign; the GATT table is the menu.

The advertisement is heard before the connection. The GATT table is read after the connection. They are not two names for the same thing.

Is the computer sending packets? Yes. After connection, every GATT operation is a packet. The app does not assemble the radio packet; the OS and controller do. It builds the ATT PDU, wraps it in L2CAP and a link-layer PDU, adds the access address and CRC, and transmits on a data channel.

The 0x52 opcode and the MXW01 frame are exact. The handle is illustrative; it is whatever the printer assigned to ae01 during discovery. The radio packet also contains fields not drawn here, including the PDU header and CRC.

A notification is an ATT Handle Value Notification: opcode 0x1B, a handle, a value. An AA event might be 1B 2A 00 + 22 21 AA 00 00 00 00 FF. The handle is illustrative; the frame is the protocol.

This is why “send it to af30” is not meaningful. There is no af30 mailbox in the connected attribute table. The advertisement bytes are metadata; the command path is a discovered handle inside ae30.

So what? Never build a driver from advertising data. Scan to find the device, connect to establish the link, discover the GATT table, and map UUIDs to handles. The advertisement tells you the printer exists; the GATT table tells you how to control it.
05

The printer’s language: frames, CRC, and rows.

The printer does not receive a document. It receives a short sequence of commands and a stream of packed image rows. The frame is the envelope around each command.

The MXW01 command frame is 22 21 <cmd> 00 <len LE16> <payload> <crc8> FF. LE16 means a two-byte little-endian integer: low byte first. A length of 4 is 04 00; a height of 208 is D0 00. The length counts only the payload; the CRC covers only the payload; FF terminates the frame.

CRC-8 is a mathematical tamper seal, not encryption. This variant uses polynomial 0x07, initial value 0x00, no reflection, final XOR 0x00, over the payload only. A different “CRC-8” can produce a different byte, and the printer will silently ignore the frame.

The print path uses A1 status, A2 intensity, A9 print request, AD flush, and AA complete; AB and B1 query battery and firmware. The A9 payload is height (LE16), 0x30 for 48 bytes per row, and a mode byte (0x00 monochrome).

Image data goes to ae03 without the frame wrapper. Each row is 48 bytes: 384 pixels, one bit each, 1 = black, least-significant-bit first. Pillow is the opposite — 0 = black, most-significant-bit first — so the driver inverts each byte and reverses the bit order. Feed rows are blank rows appended to the image and included in the A9 height.

Exhibit 6The print job in six steps
StepWhat is sentWhat it means
1 · status22 21 A1 00 01 00 00 00 FFAsk for state, battery, temperature, and errors.
2 · intensity22 21 A2 00 01 00 5D 94 FFSet heat energy; 0x5D = 93.
3 · request22 21 A9 00 04 00 D0 00 30 00 34 FF208 rows, 48 bytes/row, monochrome; wait for A9 ack.
4 · rows208 × 48 bytes on ae03One row per write, 10 ms apart.
5 · flush22 21 AD 00 01 00 00 00 FFEnd of image data.
6 · completeAA notificationPhysical print finished; not guaranteed to arrive.

For 128 content rows plus 80 feed rows: 208 rows × 48 bytes = 9,984 bytes, 208 writes, 2.08 s of deliberate pacing, and roughly 8–10 s end to end. The radio is not the bottleneck; the row cadence and print head are.

So what? The printer is a state machine with a small language. Send the right command, wait for the right acknowledgement, pace the rows, and separate physical completion from “the bytes were written.”
06

The control loop: what the codebase is doing.

The code is not “sending a print job.” It is rendering pixels, encoding a protocol, performing GATT operations, and managing a stateful device.

The application has five jobs: render content to a 1-bit bitmap, pack each row into 48 bytes, frame commands with length and CRC, transport over GATT, and orchestrate the sequence, retries, and physical state.

The call path is a straight line: CLI, web UI, or OpenCode tool → local daemon / printer manager → renderer → protocol builder → MXW01 transport → Bleak → OS Bluetooth → controller → BLE packets → printer.

Exhibit 7The software call path

The renderer never knows about BLE. The transport never knows about fonts. The manager owns the lifecycle and serializes access to the one connection.

Render. Pillow, the Python imaging library, draws text and images onto a 384-pixel-wide grayscale canvas. Fonts, margins, wrapping, baselines, and receipt columns are resolved in pixels; text is thresholded and photos are dithered. The output is a 1-bit image.

Pack and frame. The protocol layer converts each row to 48 bytes with the MXW01’s polarity and bit order, builds command frames, and computes CRC-8. These are pure functions: same input, same bytes, testable without hardware.

Transport. Bleak, a Python BLE client, connects, discovers services and characteristics, maps UUIDs to handles, subscribes to ae02 through its CCCD, and runs the sequence: status, intensity, print request, rows, flush, completion. It reassembles notifications because a notification may contain a partial frame, multiple frames, or extra bytes.

Orchestrate. The manager owns one lock, one transport, and one BLE connection. It auto-connects, retries cold starts, serializes print requests, caches status, saves history, and surfaces errors. The daemon exists because one peripheral cannot be shared safely by three front doors.

So what? The radio is commodity plumbing. The value is in the renderer, the protocol correctness, the state machine, and the user experience around a physical device that sleeps, runs out of paper, and accepts only one owner.
07

The height bug: tall letters vs no tall letters.

The printer was rendering correctly. The text was not sitting on the same line. The bug was in the coordinates, and the clue was the difference between haa and aaa.

In typography, the baseline is the line on which most letters sit. Ascenders such as h, d, and l reach above it; descenders such as g, p, and y hang below. The x-height is the height of letters such as a, c, and e. A glyph is a drawn shape; its bounding box is the rectangle around the ink of a specific string.

The renderer originally used Pillow’s anchor="la", which anchors a run to the top of its own ink box. haa has an ascender; aaa does not. Aligning the two tops puts their baselines at different heights: aaa sits higher. Mixed bold, italic, and code runs showed the same jitter.

The fix is to stop treating the ink box as the line. Font metrics — ascent and descent — are properties of the font and size, not of a string. The renderer calls font.getmetrics(), computes a shared baseline from the maximum ascent, and draws every run with anchor="ls" (left baseline). The horizontal cursor still advances by measured width; the vertical position is now shared.

The regression test uses two words: one with an ascender and one without. It finds their ink columns, groups the words, and asserts that their bottom rows are equal. If the font changes or top anchoring returns, the test fails.

Each run is aligned by its own ink-box top. The word without ascenders floats above the shared line.

The effect is exaggerated. The principle is exact: line position comes from font metrics, not from the ink of a particular string.

So what? In a renderer, “height” is a layout property, not the height of the glyphs in front of you. Use font metrics and a shared baseline; test with words that have ascenders and words that do not. The same discipline applies to receipt columns: measure pixels, not spaces.
08

The operating model: what this means.

The build is a case study in controlling a cheap, stateful, single-owner peripheral. The lessons generalize well beyond this printer.

1. Design for the medium. 384 px, 1-bit, thermal: short lines, high contrast, clear hierarchy, deliberate whitespace. The constraint is the product.

2. Trust discovery. The advertisement said af30; the command service was ae30. Scan, connect, enumerate, map UUIDs to handles. Advertising is a hint.

3. Model physical state. Paper, cover, battery, temperature, sleep, and connection ownership are part of the API. Say “wake the printer,” not “connection failed.”

4. Broker single-connection devices. A daemon serializes access, retries, caches state, and gives every front door a stable interface.

5. Measure the pipeline. 185-byte packets, but 48-byte rows with a 10 ms pause. Measure rows, pacing, acknowledgements, and physical output.

Decision checklistFor any BLE peripheral
  1. Scan and identify the device by name, address, and advertised services.
  2. Connect; do not trust the advertisement as the API.
  3. Enumerate every service and characteristic; record UUIDs, properties, and handles.
  4. Subscribe to the notification characteristic through its CCCD.
  5. Send one known query; capture the raw reply before building a print path.
  6. Test one variable at a time; use known-answer tests for frames and pixels.
  7. Preview before printing; treat physical state as part of the interface.

A cheap printer is a small computer with a radio and a secret language. The phone app was the only translator. Once you can name the layers, you can put the device behind a local API, a web page, and an agent tool — and the app stops being the gatekeeper.
